Compute on encrypted data. Reveal only the result.

PyFE4AI is a research-oriented Python library of functional encryption (FE) schemes for AI security and privacy — from single-input inner products to multi-client, threshold, decentralized and quadratic constructions, with an optional Rust core for the hot paths.

Why PyFE4AI

The functional-encryption zoo, behind one entry point

pyfe4ai.create("family/variant", config) returns a scheme's key generator and crypto class; then setup / get_decryption_keys / encrypt / decrypt — across every family, built for ML workloads.

Complete FE family coverage

SIFE, MIFE, MCFE, decentralized MCFE, threshold MIFE/MCFE, function-hiding IPE / Multi-IPE, and quadratic FE (SGP, Quad, multi-input MIQFE) — 42 (family, variant) combinations under one roof.

Five hardness assumptions, six instantiations

DDH (3072-bit groups or the ristretto255 curve) and its matrix form MDDH (Damgård), Paillier/DCR, LWE and Ring-LWE (lattice lines), and pairings (BLS12-381) — pick the assumption that fits your deployment.

ML-native adapter

pyfe4ai.ml runs SIFE and MCFE schemes for encrypted linear inference and gradient aggregation, including threshold MCFE over Ring-LWE with its decryption servers in-process. Its wrapper holds the master key and plays every party (one trust domain, for experiments) and by default refuses MIFE aggregation, partial aggregates and label reuse; the other threshold and decentralized variants go through the scheme classes. A quantization toolkit handles float ↔ integer precision.

Engineered for speed

An optional Rust extension, built by pip install when cargo is available, runs the lattice hot paths, ristretto255 and BLS12-381 pairings with the outputs of the Python reference: an MCFE Ring-LWE round of 10 000 gradient elements under standard takes about 18 ms per client and 7.5 ms to aggregate, against 345 / 157 ms on the Python backend (JSON ciphertexts, one thread).

Tested

About 4,100 tests, run in CI with and without the Rust extension (the native code is checked bit for bit against the Python reference), including status-table sync, security-profile and crypto-review regression tests, plus a structured FEError exception hierarchy.

Paper-referenced

Every scheme cites its source construction (PKC'15, CRYPTO'16/'18, ASIACRYPT'18, SCN'20, TCC'21/'22, PKC'22, IACR CiC'24, IEEE TDSC TAPFed, …) in the module docstring. Deviations from the paper are listed in the Scheme Status table.

Where FE fits

Who sees what — FE next to other privacy technologies

Functional encryption gives the holder of a functional key exactly f(x), in the clear, and nothing else about x. Other techniques draw the line elsewhere. A simplified, qualitative picture of typical deployments:

FE's limits, honestly

  • Narrow function classes: inner products and quadratic functions, not arbitrary programs.
  • The result itself is revealed: every functional key discloses one value f(x), and enough keys (e.g. η independent weight vectors for vectors of length η) determine x — which keys exist is the key authority's decision.
  • Trusted setup: most schemes need a key authority for setup and functional keys; the decentralized variants drop it for functional keys but still have a trusted setup in this library, and the threshold variants assume honest-but-curious servers (Choosing a scheme, Security & status).
How it works

One federated-learning round, three ways to deploy it

Clients encrypt their gradients under the round's label; whoever holds the functional key for the weights learns the weighted sum — not a single client's gradient. Step through it, or let it play.

  1. Once: the key authority runs setup() and gives every client its encryption key skᵢ.
  2. Each round has a label ℓ. Every client encrypts its gradient under ℓ and sends only the ciphertext — one per client and label.
  3. The authority issues the aggregator a functional key for the weights y (in mcfe/ring_lwe also bound to ℓ).
  4. The aggregator decrypts Σ yᵢ·xᵢ for label ℓ — the weighted sum, never a single gradient. Ciphertexts of different labels do not combine.
  1. The key authority gives every client its encryption key and each of the s = 3 servers its share of the functional key for y; with t < s the LWE layers use a replicated sharing (the default).
  2. Clients encrypt as usual under ℓ; the ciphertexts reach the servers (in tMCFE-Ring-LWE tagged for each server).
  3. An enrolled set of t = 2 servers computes partial decryptions with share_decrypt; the LWE layers flood them with noise. Server 3 can stay offline.
  4. A combiner — any party, it holds no secret — joins the t partials with combine_decrypt and decodes Σ yᵢ·xᵢ. Fewer than t servers learn nothing beyond the result.
  1. No authority for functional keys — but the setup is trusted: in this library one key generator samples every client's keys, including the pairwise zero-sum secrets, in process.
  2. Each round, every client sends its ciphertext; for each functional key it also sends its own share of the key for y (every round in dMCFE-Ring-LWE, whose keys are bound to the label).
  3. The aggregator combines the shares into the functional key and decrypts Σ yᵢ·xᵢ.

Threshold servers are assumed honest-but-curious: a partial decryption carries no proof of correctness. pyfe4ai.ml runs MCFE — and the servers of mcfe/ring_lwe_threshold — in one process for experiments. Details: Threshold decryption and the ML adapter.

Inside the library: one call through the stack

Python on top, one backend interface in the middle, and two implementations of it: the Python reference and the optional Rust extension, which computes the same values. Follow a call down to the Rust core and back.

  1. pyfe4ai.create("mcfe/ring_lwe", cfg) — the registry finds the scheme by id and builds its key generator, the config completed by the security profile; you get kg and the class MCFERingLWE.
  2. client.encrypt_lst_ndarray([grad], label=ℓ) — the scheme packs the tensor into chunks: one Ring-LWE ciphertext per chunk, each with its own label pad.
  3. Primitives: the label is hashed to Zq, and the noise comes from the scheme's sampler — exact (FACCT) Gaussians by default for the Ring-LWE family.
  4. backend.ring(q, n).encrypt_tensor(…) — under auto the extension is built and q < 2253 has the root of unity it needs, so the native implementation runs.
  5. pyfe4ai._rust_native runs the rust/core kernels: one call per tensor with the GIL released, chunks in parallel with PYFE4AI_THREADS, one ChaCha20 stream per chunk from one OS seed, overwritten when the call ends.
  6. The ciphertexts return to your code — JSON by default for mcfe/ring_lwe, or binary with ct_format="binary".
  1. encrypt_gradient(grad, wrapper, nid="c1", label=ℓ) — one client's step of a federated round.
  2. pyfe4ai.ml reserves (client, ℓ) — a second encryption under ℓ is refused — and takes the client's crypto object, which the wrapper built from the registry.
  3. The scheme scales the floats to integers at the wrapper's precision and packs them into chunks …
  4. … through the same primitives, backend interface and Rust kernels as a direct call.
  5. An EncryptedGradient comes back, ready to serialise for the aggregator (to_dict()).
  1. PYFE4AI_BACKEND=python — or the extension is not built, or the parameters are outside what it handles (moduli of 2253 or more, rings without a 2n-th root of unity, wider Gaussians).
  2. The layers above the backend run the same code as before.
  3. The backend interface hands the operation to the Python reference (backend/python_impl: gmpy2, NumPy).
  4. Same results, only slower: the tests run every backend operation through both implementations and require the same outputs. Without the extension the library says so once per process (FEWarning; not under an explicit python).

Simplified: the lanes on the left carry the call down (amber) and the result back up (teal); the layers above the backend also share pyfe4ai.core. What runs natively is listed in the docstring of pyfe4ai.backend and in Threads, processes and copies.

Python is the reference

The extension computes the reference's values — same NTT roots and tables, samplers and hash reductions — and tests compare the two.

One random source per call

A tensor call expands one 32-byte OS seed with ChaCha20, one stream per chunk; seed and states are overwritten when it ends.

GIL released, threads optional

One native call per tensor; PYFE4AI_THREADS=k lets it use k threads (default 1).

Unsupported inputs fall back

Inputs it does not handle go to the reference: moduli ≥ 2253, rings without the root of unity, wider Gaussians.

Scheme families

42 schemes, one registry

A scheme is named "family/variant": the family says who encrypts and who decrypts, the variant which assumption and construction it uses. pyfe4ai.list_schemes() and pyfe4ai.get_scheme_status("family/variant") answer the same questions at runtime.

SIFE

11

single-input

One encryptor; the holder of a key for y learns ⟨x, y⟩ — one party's vector scored by another party's linear model.

MIFE

11

multi-input

n clients each encrypt a slot; the key holder learns Σ⟨xᵢ, yᵢ⟩. No labels: for one-shot joint inputs, not for repeated rounds.

MCFE

17

multi-client, labelled

Clients encrypt under a shared label, and only ciphertexts of one label combine — federated aggregation, one label per round.

Quadratic

3

SGP · Quad · MIQFE

The key holder learns xᵀFy (sgp, quad), or the cross-user quadratic terms of several clients (miqfe).

  • 6 threshold — the functional key shared among s servers, any t decrypt
  • 5 decentralized — no authority for functional keys (trusted setup)
  • 7 function-hiding — keys also hide the weights
  • 4 refused under standard

Use cases

Built for privacy-preserving ML

Functional encryption reveals a chosen function of the data — not the data itself.

Secure aggregation in federated learning

Clients encrypt local gradients with MCFE-DDH (CDGPP18), the DCR, LWE and MDDH constructions of ABMPSW20, or MCFE-Ring-LWE (BMMS21), which under standard encrypts 10 000 gradient elements in about 18 ms per client with the Rust extension (0.35 s in pure Python); the aggregator's functional key decrypts only the weighted sum. dMCFE variants need no authority for functional keys (their setup, which samples every client's keys in-process, is still trusted).

examples/ml_fl_aggregation.py

Encrypted inference

Score features with a linear model (SIFE), or evaluate a bilinear form xTFy with quadratic FE (BLS12-381 from the Rust extension), directly over ciphertexts — the model owner learns the result, never the raw features.

examples/ml_encrypted_inference.py examples/quadratic_quad_minimal.py

Threshold aggregation

tMCFE variants (TAPFed-style) split decryption across t-of-s servers that are assumed honest-but-curious; their LWE, Ring-LWE and pairing threshold layers are experimental. For mcfe/ring_lwe_threshold the ML adapter runs the servers in-process — for experiments — and shows the messages of a deployment (partial_decrypt_gradients, combine_partial_decryptions).

Quickstart

From clone to first inner product

Encrypt a vector, hand out a functional key, learn only the inner product. Demo parameters are toy-sized: sec_param is a modulus bit length, not a security level; "security_profile": "standard" selects 128-bit-oriented parameters, except for pairings (BLS12-381, about 120–126-bit) and the schemes it refuses (Security Profiles).

install · shell
# from source
git clone https://github.com/spire-studio/pyfe4ai.git
cd pyfe4ai
conda env create -f environment.yml
conda activate pyfe4ai
# with cargo on the PATH this also builds the optional Rust
# extension (BLS12-381 for the pairing & quadratic FE)
pip install -e ".[test]"

# other pairing curves (charm-crypto): GMP, OpenSSL, PBC first
pip install -e ".[test,pairing]"

# run the core test suite
python -m pytest -m core -q

sife_ddh.py

import pyfe4ai

x, y = [2, 1, 3], [4, 5, 6]

# sec_param = 128 is a toy modulus size: fast, NOT secure. For a
# 3072-bit group pass {"security_profile": "standard", "eta": 3}.
kg, SIFEDDH = pyfe4ai.create("sife/ddh", {"sec_param": 128, "eta": 3})
kg.setup()
pp, sk = kg.get_public_parameters(), kg.get_private_keys()
dk = kg.get_decryption_keys("sid_0",
        credentials={"fusion_weight": y})

ct = SIFEDDH({"precision": 3, "keys": {"pp": pp, "sk": sk}}).encrypt(x)
result = SIFEDDH({"precision": 3, "keys": {"pp": pp}}).decrypt(ct, dk, y)
print(result)  # 31 = ⟨x, y⟩

mcfe_ddh.py

import pyfe4ai

x = {"alice": [1, 2], "bob": [3, -1], "carol": [0, 4]}
y = {"alice": [2, 1], "bob": [1, 1], "carol": [-1, 3]}

kg, MCFEDDH = pyfe4ai.create("mcfe/ddh", {"eta": 2, "n": 3, "lst_nid": list(x)})
kg.setup()
pp = kg.get_public_parameters()

# every client encrypts its own vector under the round's label
label = "round-1"
cts = {}
for nid in x:
    client = MCFEDDH({"id": nid, "keys": {"pp": pp, "sk": kg.get_private_keys(nid)}})
    cts[nid] = client.encrypt(x[nid], label)

# the functional key reveals only the weighted sum, for one label
dk = kg.get_decryption_keys("aggregator", credentials={"fusion_weight": y})
aggregator = MCFEDDH({"id": "aggregator", "keys": {"pp": pp}})
print(aggregator.decrypt(cts, dk, y, label))  # 18

fl_round.py

import numpy as np
from pyfe4ai.ml import FESchemeWrapper, aggregate_gradients, encrypt_gradient

clients = ["c0", "c1", "c2"]
# the wrapper runs the key generator and plays every party: experiments only
wrapper = FESchemeWrapper("mcfe", "ring_lwe",
                          {"eta": 1, "n": 3, "lst_nid": clients,
                           "bound_x": 10**4, "bound_y": 10},
                          precision=3)
grads = {nid: np.random.default_rng(i).uniform(-1, 1, 1000)
         for i, nid in enumerate(clients)}
enc = {nid: encrypt_gradient(g, wrapper, nid=nid, label="round-1")
       for nid, g in grads.items()}
total = aggregate_gradients(enc, wrapper, {nid: 1 for nid in clients},
                            label="round-1")
print(np.allclose(total, sum(grads.values()), atol=1e-2))  # True

Security & status

Honest about what is reviewed — and what is not

Every registered scheme carries a review status in the registry, reported at runtime by pyfe4ai.get_scheme_status("family/variant").

Security profiles

"toy" default

Fast and not secure: sec_param is a modulus bit length, LWE dimensions default to 32–64 and the Ring-LWE dimension to 32.

"standard"

Aims at 128-bit security: 3072-bit discrete-log groups (RFC 3526) and DCR moduli, lattice-estimator-sized LWE and Ring-LWE dimensions, stat_param 128. Pairings run on BLS12-381, about 120–126-bit (a FESecurityWarning says so).

Refused under standard — no parameter set both secure and usable: sife/fullysec_lwe mife/fullysec_lwe mife/lwe_threshold mcfe/paillier_decentralized

Trust model

  • Threshold servers are honest-but-curious: partial decryptions carry no proof of correctness; redundant enrolled sets can detect a deviating server.
  • Decentralized MCFE needs no authority for functional keys, but its setup is trusted.
  • The ML adapter holds the master key and plays every party: one trust domain, for experiments.
  • No side-channel hardening; authenticated channels between parties are assumed.
